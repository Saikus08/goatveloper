AI tooling setup looks personal at first.

Install the CLI. Add a few agents. Connect a couple of MCP servers. Keep some prompts around. Move fast.

That works while the setup lives only in one developer's machine. It stops working when the repository starts depending on those decisions.

In URadar, the local workflow had OpenCode agents, Omo continuation state, OpenSpec changes, Context7, GitHub MCP, and ClickUp MCP all sitting near the same project. Some of that belongs in git. Some of it absolutely does not.

That is where AI workspace configuration stops being personal setup. It becomes repository governance.

## The Mental Shift

Junior engineers often see tooling config as an all-or-nothing choice:

1. Commit everything so the team has the same setup.
2. Commit nothing because some of it might be local.

Both choices are too blunt.

A senior engineer asks a different question: what is the contract this repository should own?

The repository should own shared behavior: agents, commands, context, specs, safety rules, and reproducible package metadata.

The developer's machine should own identity: tokens, OAuth state, sessions, local caches, generated dependencies, and continuation history.

The difference matters because the dangerous files are usually next to the useful ones.

## Start With The Spec

The first real step was not editing `.gitignore`.

The first step was creating an OpenSpec change:

```text
openspec/changes/version-ai-workspace-config/
  proposal.md
  tasks.md
```

That is a small process decision, but it changes the quality of the work.

Without a spec, the task can collapse into a quick ignore-file patch. With a spec, the work has goals, non-goals, acceptance criteria, and verification steps before the implementation starts.

The proposal made the boundary explicit:

- make shared AI workspace configuration reproducible;
- keep local auth, tokens, sessions, and generated files out of git;
- document the difference between project configuration and personal machine state;
- avoid changing application runtime behavior.

That last point is important. This was not a product feature. It was developer workflow infrastructure. Mixing those two concerns would make the change harder to review.

## The Ticket And Branch Boundary

The work also got a ClickUp task before implementation continued.

The branch name carried the task id:

```text
cu-86ahnww2r-version-ai-workspace-config
```

That is not ceremony for ceremony's sake. It gives the change a traceable path:

1. OpenSpec explains why the work exists.
2. ClickUp tracks the delivery task.
3. The branch connects the code to the task.
4. The final diff can be reviewed against the spec.

For small changes, it is tempting to skip that structure. But shared tooling changes have a long tail. Months later, someone may wonder why `.omo/` is ignored or why `.opencode/package-lock.json` is versioned. The answer should be findable without asking the person who made the change.

## What Belongs In Git

URadar already had useful shared OpenCode configuration:

```text
AGENTS.md
opencode.jsonc
.safety-net.json
.opencode/agents/
.opencode/commands/
.opencode/context/
openspec/
```

Those files describe how the repo expects agents to behave, which commands exist, what project context should be loaded, and which safety rules apply.

That is project knowledge.

It is safe to share because it does not contain a user's credentials. More importantly, it is valuable to share because it keeps collaborators from rebuilding the same workspace rules from memory.

The change also made `.opencode/package.json` and `.opencode/package-lock.json` trackable. That pins the OpenCode plugin dependency for the repository-level setup.

This is the same reasoning as normal application dependencies: if a project depends on a package to behave consistently, the package metadata belongs in source control.

There was one dependency detail worth making explicit. The `.opencode` package should be named, marked `private`, and declare the Node.js range required by its dependency tree. In this case, that means using Node `^20.17.0` or `>=22.9.0` for `.opencode` installs.

A new contributor should be able to recreate the repository-local plugin install with:

```bash
npm --prefix .opencode ci
```

## What Must Stay Local

The local-only side is just as important.

URadar now treats these as local machine state:

```text
.omo/
.opencode/node_modules/
.opencode/bun.lock
.opencode/.env*
.opencode/**/*.env*
.opencode/**/tokens/
.opencode/**/auth/
.opencode/**/sessions/
.opencode/**/cache/
.opencode/**/*token*.json
.opencode/**/*auth*.json
.opencode/**/*session*.json
.opencode/**/*cache*.json
```

`.omo/` contains continuation and session state. That can be useful locally, but it is not a repository contract.

`.opencode/node_modules/` is generated dependency output. It should be recreated from package metadata.

`.opencode/bun.lock` stays local because the repo standard is npm. Versioning both npm and Bun lockfiles would send mixed signals about the package manager contract.

The env, token, auth, session, and cache patterns are defense-in-depth. They are intentionally scoped to directories and JSON-like local state so the repo does not accidentally hide future documentation or source files just because a filename contains a word like `auth`.

The rule stays stable: credentials and personal state do not belong in git.

## MCP Auth Is Not Project Configuration

GitHub MCP and ClickUp MCP are useful because they connect the development workflow to external systems.

That does not make their auth state project configuration.

The repository can document that the workflow expects GitHub and ClickUp MCP to exist locally. It can document how the project uses ClickUp tasks and branch names. It can even share non-secret MCP endpoint definitions when they contain no credentials.

But it should not own a developer's OAuth state, API token, personal access token, cached task response, or session file.

That distinction is easy to miss. A junior implementation might say, "commit the MCP config so everyone has the same tools." A senior implementation separates the reusable contract from the private identity that satisfies it.

## Gitignore As A Governance Tool

`.gitignore` is often treated as cleanup.

In this kind of change, it is policy.

The root `.gitignore` now protects repo-level local state like `.omo/` and sensitive `.opencode` patterns. The nested `.opencode/.gitignore` keeps dependency output and Bun lock state local while allowing npm package metadata to be versioned.

That split matters because the repository needed two different rules at the same time:

1. Do version `.opencode/package.json` and `.opencode/package-lock.json`.
2. Do not version `.opencode/node_modules/`, sessions, auth, caches, or env files.

The interesting part is not the syntax. The interesting part is the ownership model behind the syntax.

## The Runtime Contract

The final shape was documented in a runtime spec:

```text
openspec/specs/ai-workspace-configuration.md
```

That spec lists shared configuration, local-only state, MCP boundaries, maintenance rules, and verification commands.

It was also linked from:

```text
openspec/project.md
openspec/specs/README.md
```

This keeps the boundary discoverable from the same place as other project contracts.

That is another senior habit: do not hide important operational rules in the commit diff. Put them where future work will look.

## Tests That Protect The Boundary

This change did not need application unit tests.

It needed repository checks.

The verification focused on whether git sees the right files:

```bash
git check-ignore .omo/run-continuation/example.json
git check-ignore .opencode/node_modules/example
git check-ignore .opencode/.env.local
git ls-files .omo .opencode/node_modules
git ls-files .opencode/agents .opencode/commands .opencode/context opencode.jsonc .safety-net.json
```

The first group confirms local-only files stay ignored.

The second group confirms no generated or session state is already tracked.

The third group confirms shared config is visible to git.

There was also a package metadata check inside `.opencode`:

```bash
npm install --package-lock-only --ignore-scripts
```

That confirmed the lockfile was consistent without installing dependencies or running package scripts.

This is the same testing mindset applied to a different surface. The behavior being protected is not an HTTP response or a React component. It is the repository boundary.

## The Practical Checklist

For the next shared tooling setup, I would start with this checklist:

1. List the files that describe shared behavior.
2. List the files that contain local identity, generated output, or session state.
3. Decide which package manager owns the tooling dependency metadata.
4. Write the boundary in a spec before changing ignore rules.
5. Create a tracked task so the change has a reason outside the diff.
6. Name the branch with the task id.
7. Version agents, commands, context, safety rules, and package metadata when they are credential-free.
8. Ignore `.env`, token, auth, session, cache, continuation, and dependency output files.
9. Verify with `git check-ignore` and `git ls-files`, not just visual inspection.
10. Review the final diff as if a secret accidentally slipped in.

## The Bigger Lesson

Senior engineering is often less about writing more code and more about deciding where a boundary should live.

This case was not complex because the implementation was large. It was complex because the useful files and the dangerous files lived close together.

OpenCode agents are useful project knowledge. Omo session files are local execution history. OpenSpec belongs in git. MCP auth belongs to the developer. Package metadata can be shared. Installed dependencies should be regenerated.

The difference between a junior and senior solution is not that one knows `.gitignore` syntax better.

It is that the senior solution leaves behind a contract: what the repo owns, what the machine owns, how to verify the boundary, and where the next developer can read the reasoning.
